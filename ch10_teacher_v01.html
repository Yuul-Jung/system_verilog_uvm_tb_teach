00개요 · 검증기가 오류도 검출하는가

제09장은 참조 모델과 실제 출력을 매 클록 비교했습니다. 이번 장은 Corner Case(코너 케이스, 경계조건)와 Fault Injection(폴트 인젝션, 오류 주입)을 통해 정상 출력뿐 아니라 검증기의 실패 판정도 시험합니다. 원본 PWM 회로에 결함을 넣지 않고, 테스트벤치의 입력 요청과 관찰 경로에만 오류를 주입합니다.

선행 설계 학습안내서: 제2부 사용자 AXI IP와 주변장치(amd_soc_p2) 04.2장 「RTL · AXI 풀이」 02절 「설정 Shadow와 출력 Active를 분리」 및 06절 「독립 PWM Core 전체」. 이번 DUT는 pwm_core.v이며 AXI 래퍼와 보드는 검증 범위 밖입니다.

정상 회로를 넣었을 때 PASS만 출력하는 검증기는 비교가 빠져 있어도 통과할 수 있습니다. 그래서 일부러 잘못된 관찰값이나 누락된 요청을 만들어 검사기가 실패 경로로 들어가는지 확인합니다. 부정 시험은 ‘예상한 이유로 실패해야 성공’이라는 두 단계 판정입니다.

이번 장은 0%·100%라는 경계값, 동작 중 리셋, 설정 완료 기한을 다룹니다. 원본 RTL을 변이시키지 않고 TB 외부 경로에 주입하므로 검출력을 확인한 범위 역시 그 두 경로에 한정됩니다.

01원본 RTL과 경계조건

클록은 10ns, 주기는 8클록(80ns)입니다. 정상 극성, 출력 활성 조건에서 듀티 0은 항상 LOW, 듀티 8은 항상 HIGH입니다. 설정은 주기 경계에서 반영됩니다.

reference_rtl/pwm_core.v · Verilog
`timescale 1ns/1ps
// P2-04: 보드와 무관한 단일 채널 범용 PWM 코어.
// (추가) period와 duty는 클록 횟수 단위. 0%/100%는 지속 LOW/HIGH.
// (추가) 설정은 주기 마지막 경계에서만 활성값으로 반영.
module pwm_core #(
    parameter [31:0] RESET_PERIOD = 32'd100000
)(
    input  wire        clk,
    input  wire        resetn,
    input  wire        cfg_apply,
    input  wire [31:0] cfg_period,
    input  wire [31:0] cfg_duty,
    input  wire        cfg_enable,
    input  wire        cfg_polarity,
    output wire        pwm_out,
    output reg         pending,
    output reg [31:0] active_period,
    output reg [31:0] active_duty,
    output reg         active_enable,
    output reg         active_polarity
);
    reg [31:0] counter;
    reg [31:0] shadow_period;
    reg [31:0] shadow_duty;
    reg        shadow_enable;
    reg        shadow_polarity;

    wire boundary = (counter >= active_period - 32'd1);
    wire duty_high = (counter < active_duty);

    // (주의) enable=0이면 polarity와 관계없이 LOW로 차단.
    // (설명) 기본 polarity에서 active_duty=0이면 항상 LOW,
    //         active_duty=active_period이면 항상 HIGH.
    assign pwm_out = resetn && active_enable &&
                     (active_polarity ? !duty_high : duty_high);

    always @(posedge clk) begin
        if (!resetn) begin
            counter         <= 32'd0;
            active_period   <= RESET_PERIOD;
            active_duty     <= 32'd0;
            active_enable   <= 1'b0;
            active_polarity <= 1'b0;
            shadow_period   <= RESET_PERIOD;
            shadow_duty     <= 32'd0;
            shadow_enable   <= 1'b0;
            shadow_polarity <= 1'b0;
            pending         <= 1'b0;
        end else begin
            if (boundary) begin
                counter <= 32'd0;
                if (pending) begin
                    active_period   <= shadow_period;
                    active_duty     <= shadow_duty;
                    active_enable   <= shadow_enable;
                    active_polarity <= shadow_polarity;
                    pending         <= 1'b0;
                end
            end else begin
                counter <= counter + 32'd1;
            end
            // (추가) 경계와 APPLY가 겹치면 새 값은 다음 경계에 적용.
            // 여러 APPLY가 겹치면 최종 요청값을 우선하는 단일 Shadow 구조.
            if (cfg_apply) begin
                shadow_period   <= cfg_period;
                shadow_duty     <= cfg_duty;
                shadow_enable   <= cfg_enable;
                shadow_polarity <= cfg_polarity;
                pending         <= 1'b1;
            end
        end
    end
endmodule
조건기대 출력
active_duty=0, enable=1, polarity=0LOW
active_duty=8, enable=1, polarity=0HIGH
active_enable=0극성과 무관하게 LOW
resetn=0상승 에지와 무관하게 LOW

이번 실행은 정상 극성 및 enable=1에서 두 듀티 경계를 시험합니다. 비활성화·반전 시험은 제09장을 참고합니다. 주기 0이나 범위 밖 듀티, AXI 레지스터 검사는 포함하지 않습니다.

경계값의 회로 근거

period=8에서 counter는 0~7입니다. duty=0이면 counter<0은 항상 거짓, duty=8이면 counter<8은 항상 참입니다. 정상 극성·enable=1일 때 두 경우는 계속 LOW와 계속 HIGH가 됩니다. 비트 수가 32라고 모든 32비트 입력이 의미 있는 듀티인 것은 아닙니다. 이 시험은 0과 period라는 명확한 경계 두 개를 사용합니다.

measured_pwm은 pwm_out ^ corrupt_observation입니다. 실제 DUT 출력이 정상 HIGH임에도 측정값만 LOW가 되면 관찰 오류를 검출합니다. 요청 누락 시험에서는 첫 0% 설정을 정상 적용한 뒤 다음 듀티 8 요청의 펄스를 생략합니다. 기존 0% 상태가 유지되어야 의도된 타임아웃으로 인정합니다. 두 주입 옵션을 함께 선택하면 오류로 종료합니다.

그림 읽기 · DUT 결함과 측정 경로 오류 구별

measured_pwm은 pwm_out ^ corrupt_observation입니다. 반전 비트가 0이면 그대로이고 1이면 반대입니다. 정상 HIGH=1과 1을 XOR하면 측정값은 0이 됩니다. 실제 pwm_out은 유지하므로 ‘DUT 출력이 틀렸다’와 ‘정상 출력을 잘못 관찰했다’를 구분할 수 있습니다.

check_outputs는 먼저 공개 상태가 정상인지 확인합니다. 그 뒤 measured_pwm이 틀리면서 원래 pwm_out은 기대값과 맞을 때만 전용 DETECTED_INJECTED_FAULT를 냅니다. 아무 Fatal이나 주입 성공으로 인정하면 초기화 오류나 연결 실패까지 검출력 증거로 오인할 수 있습니다.

03설정 적용 대기와 시간 계약

request_duty()는 하강 에지에서 입력을 바꾸고 다음 하강 에지에 펄스를 종료합니다. 정상 시나리오의 요청 위치에서는 pending이 1이어야 합니다. 일반화된 연속 요청 검사와는 구별합니다. check_constant_window()는 pending=0과 active_duty의 목표값을 모두 기다리며, 종료하지 않으면 최대 10번 상승 에지 관찰 후 실패합니다.

위 수치는 8클록 경계와 TB의 에지 대기를 독립 계산한 예상 시간입니다. 예를 들어 두 번째 요청을 누락하면 260ns에 요청 태스크가 끝난 뒤 266~356ns의 10개 관찰 동안 active_duty가 0입니다. 356ns에 적용 타임아웃을 검출할 것으로 예상됩니다. 정상 요청을 적용한 뒤 관찰값만 반전하는 모드는 첫 비교인 336ns에서 실패할 것으로 예상됩니다.

10클록은 이 고정 8클록 실습의 대기 상한입니다. 다른 주기로 바꾸면 상한도 재설계해야 합니다. 전체 실행의 5000ns 안전 상한은 별개의 무한 대기 방지 장치입니다.

판서 · pending 하나만 보면 생기는 거짓 완료

요청 누락 모드에서는 기존 0% 상태의 pending이 0입니다. pending=0만 완료 조건으로 쓰면 새 duty=8이 적용되지 않았는데도 즉시 통과합니다. 그래서 pending===0과 active_duty===목표가 모두 맞아야 대기를 끝냅니다.

두 번째 요청 task가 끝나는 260ns 뒤 최대 열 상승 에지를 관찰하면 266·276·286·296·306·316·326·336·346·356ns입니다. 그동안 기존 period=8·duty=0·enable=1·polarity=0·pending=0·출력0이 유지되어야 의도된 요청 누락으로 해석할 수 있습니다. 다른 상태가 틀리면 TIMEOUT_BASELINE 실패로 따로 분류합니다.

최대 열 클록은 고정 주기8에 맞춘 계약입니다. 정상 적용 대기는 이 한계 안에서 끝나고, 전체 5,000ns watchdog는 별도의 마지막 안전장치입니다. 두 기한을 같은 검사로 설명하지 않습니다.

04동작 중 리셋 · 출력과 상태를 분리

원본은 출력 조합 차단과 내부 동기 리셋을 함께 사용합니다. 리셋을 인가하기 전에 실제 출력이 HIGH인지 먼저 확인합니다. 이미 LOW이면 리셋 차단 기능을 검증할 수 없습니다.

495ns다음 상승 에지내부 상태 초기화
496ns에지 이후 관찰period=8, duty=0, enable=0, polarity=0, pending=0, pwm_out=0
500ns하강 에지resetn HIGH

리셋 전에는 듀티 100%로 출력이 계속 HIGH입니다. 따라서 489ns의 LOW는 495ns의 내부 레지스터 초기화보다 먼저 발생해야 합니다. 동시에 489ns에는 활성 주기 8, 듀티 8, enable 1, polarity 0, pending 0을 유지해야 합니다. 이 선행 상태 검사로 레지스터가 리셋 인가 즉시 비동기적으로 초기화되는 결함을 구별합니다. 그 후 다시 100%를 요청해 재시작까지 확인합니다.

리셋 판서 · 출력이 먼저 내려가고 상태는 나중에 바뀐다

두 번째 창의 마지막 비교는 486ns입니다. 여기서 HIGH 선행 조건을 확인하고 2ns 뒤 488ns에 리셋을 내립니다. 489ns에는 pwm_out=0이지만 Active는 period8·duty8·enable1을 유지해야 합니다. 495ns 상승 에지에서 레지스터를 리셋하고 496ns에는 duty0·enable0을 확인합니다.

출력만 확인하면 레지스터를 실수로 비동기 리셋한 구현도 통과할 수 있습니다. 그래서 에지 전 상태 보존 검사와 에지 후 초기화 검사를 나눕니다. 원본 동작은 ‘조합 출력 차단’과 ‘동기식 저장 상태 초기화’가 함께 있는 것이며 resetn 이름만 보고 둘을 한 종류로 부르지 않습니다.

// 원본 pwm_core는 수정하지 않고 공개 포트만 사용한다.
module tb_pwm_corner_reset_timeout;
    reg clk = 1'b0;
    reg resetn = 1'b0;
    reg cfg_apply = 1'b0;
    reg [31:0] cfg_period = 32'd8, cfg_duty = 32'd0;
    reg cfg_enable = 1'b1, cfg_polarity = 1'b0;
    wire pwm_out, pending, active_enable, active_polarity;
    wire [31:0] active_period, active_duty;
    integer checks = 0;
    integer requests = 0;

    // (추가) 관찰값 오류 및 설정 요청 누락을 DUT 외부에서 주입한다.
    // +INJECT_FAULT: 측정 경로만 반전 → 스코어보드 검출 시험.
    // +INJECT_TIMEOUT: 듀티 8 요청을 누락 → 적용 기한 검출 시험.
    reg inject_fault = 1'b0;
    reg inject_timeout = 1'b0;

        .clk(clk), .resetn(resetn), .cfg_apply(cfg_apply),
        .cfg_period(cfg_period), .cfg_duty(cfg_duty),
        .cfg_enable(cfg_enable), .cfg_polarity(cfg_polarity),
        .pwm_out(pwm_out), .pending(pending),
        .active_period(active_period), .active_duty(active_duty),
        .active_enable(active_enable), .active_polarity(active_polarity)
    );

    initial begin
        #5000;
        $fatal(1, "FAIL GLOBAL_TIMEOUT");
    end

    // (변경) 상태 검사와 PWM 측정값 검사를 구별한다.
    // 주입 시험에서 DUT 원본 pwm_out은 변경하지 않는다.
    task automatic check_outputs(
        input [31:0] expected_duty,
        input expected_pwm,
        input expected_pending
    );
        begin
            if (active_period !== 32'd8 ||
                active_duty !== expected_duty ||
                active_enable !== 1'b1 ||
                active_polarity !== 1'b0 ||
                pending !== expected_pending) begin
                $fatal(1, "FAIL STATE duty=%0d pending=%b", active_duty, pending);
            end

            if (measured_pwm !== expected_pwm) begin
                if (corrupt_observation && (pwm_out === expected_pwm))
                    $fatal(1, "DETECTED_INJECTED_FAULT dut=%b measured=%b",
                        pwm_out, measured_pwm);
                $fatal(1, "FAIL PWM actual=%b expected=%b",
                    measured_pwm, expected_pwm);
            end
            checks = checks + 1;
        end
    endtask

    // (변경) +INJECT_TIMEOUT이면 DUT가 아니라 외부 cfg_apply를 누락한다.
    task automatic request_duty(input [31:0] duty);
        reg withhold_apply;
        begin
            @(negedge clk);
            withhold_apply = inject_timeout && (duty == 32'd8);
            cfg_period = 32'd8;
            cfg_duty = duty;
            cfg_enable = 1'b1;
            cfg_polarity = 1'b0;
            cfg_apply = !withhold_apply;
            @(negedge clk);
            cfg_apply = 1'b0;
            requests = requests + 1;
            if (!withhold_apply && pending !== 1'b1)
                $fatal(1, "FAIL request not pending");
            if (withhold_apply)
                $display("INJECT: cfg_apply intentionally withheld");
        end
    endtask

    // (변경) pending과 active_duty를 모두 확인한 뒤 전체 두 주기를 검사한다.
    task automatic check_constant_window(
        input [31:0] duty,
        input expected_level
    );
        integer i;
        begin
            request_duty(duty);

            // 최대 10클록 동안 새 설정의 실제 적용을 기다린다.
            for (i = 0; i < 10 &&
                 ((pending !== 1'b0) || (active_duty !== duty));

                @(posedge clk);
                #1;
                // (추가) 요청 누락 시험에서 기존 정상 0% 상태를 확인한다.
                // 다른 상태 오류를 의도된 타임아웃 성공으로 오인하지 않는다.
                if (inject_timeout && duty == 32'd8 &&

                     active_duty !== 32'd0 || active_enable !== 1'b1 ||

                $fatal(1, "FAIL APPLY_TIMEOUT duty=%0d", duty);

            for (i = 0; i < 16; i = i + 1) begin

                #1;

            end
            corrupt_observation = 1'b0;
        end
    endtask

    initial begin
        inject_fault = $test$plusargs("INJECT_FAULT");
        inject_timeout = $test$plusargs("INJECT_TIMEOUT");
        if (inject_fault && inject_timeout)
            $fatal(1, "FAIL: 동시에 두 오류 모드를 선택하지 마세요");

        // 동기 리셋: 첫 상승 에지 이후 초기 레지스터를 검사한다.
        @(posedge clk); #1;
        if (active_period !== 32'd8 || active_duty !== 32'd0 ||
            active_enable !== 1'b0 || active_polarity !== 1'b0 ||
            pending !== 1'b0 || pwm_out !== 1'b0)
            $fatal(1, "FAIL initial reset");
        @(negedge clk);
        resetn = 1'b1;

        check_constant_window(32'd8, 1'b1); // 100%: 항상 HIGH

        // (추가) 출력이 HIGH인 상태에서 리셋 차단을 검사한다.
        if (pwm_out !== 1'b1)
            $fatal(1, "FAIL RESET_PRECONDITION");

        #1;
        if (pwm_out !== 1'b0)

        // (추가) 다음 상승 에지 이전에는 활성 레지스터가 보존되어야 한다.
        // 비동기 레지스터 리셋으로 잘못 구현한 경우를 검출한다.
        if (active_period !== 32'd8 || active_duty !== 32'd8 ||
            active_enable !== 1'b1 || active_polarity !== 1'b0 ||
            pending !== 1'b0)
            $fatal(1, "FAIL PRE_EDGE_STATE");
        @(posedge clk); #1;
        if (active_period !== 32'd8 || active_duty !== 32'd0 ||
            active_enable !== 1'b0 || active_polarity !== 1'b0 ||
            pending !== 1'b0 || pwm_out !== 1'b0)
            $fatal(1, "FAIL synchronous register reset");

        resetn = 1'b1;

        check_constant_window(32'd8, 1'b1); // 리셋 뒤 재설정

        $display("PASS CH10 requests=%0d checks=%0d", requests, checks);
        $finish;
    end

실습 루트로 돌아가 다음 스크립트를 저장합니다. 한 번 컴파일하고 세 모드를 실행합니다. 정상 시험의 종료 상태와 정확한 완료 문자열을 확인하며, 부정 시험은 비정상 종료와 전용 진단 문자열을 함께 확인합니다.

#!/usr/bin/env bash
# 제10장: 정상 경계값 시험 + 오류 주입 2건(예상 실패)을 자동 확인한다.
# 오류 주입은 테스트벤치의 관찰 경로/입력 요청에만 적용한다. DUT 수정 없음.

DUT_PATH="${DUT_PATH:-$ROOT/reference_rtl/pwm_core.v}"
TB_PATH="$ROOT/tb/ch10/tb_pwm_corner_reset_timeout.sv"
OUT="$ROOT/.build/ch10"

for tool in iverilog vvp; do
  if ! command -v "$tool" >/dev/null 2>&1; then
    echo "NOT_RUN: $tool 미설치. sudo apt update && sudo apt install iverilog" >&2
    exit 2
  fi
done
if [[ ! -f "$DUT_PATH" ]]; then
  echo "FAIL: 원본 DUT 파일 없음: $DUT_PATH" >&2
  exit 1
fi

mkdir -p "$OUT"
# 이전 실행의 파형을 이번 실행 결과로 오인하지 않도록 정리한다.
rm -f "$OUT/ch10_pwm_corner_reset_timeout.vcd" "$OUT/normal.vcd" \
  "$OUT/fault_injection.vcd" "$OUT/apply_timeout.vcd"
iverilog -g2012 -DVCD -s tb_pwm_corner_reset_timeout -o "$OUT/sim.vvp" \
  "$DUT_PATH" "$TB_PATH" 2>&1 | tee "$OUT/build.log"

# ① 정상 사례: 실제 DUT가 0%·100%·중간 리셋·재설정을 통과해야 함.
(cd "$OUT" && vvp ./sim.vvp | tee normal.log)
if [[ -f "$OUT/ch10_pwm_corner_reset_timeout.vcd" ]]; then
  mv "$OUT/ch10_pwm_corner_reset_timeout.vcd" "$OUT/normal.vcd"
fi
if ! grep -q '^PASS CH10 requests=3 checks=48$' "$OUT/normal.log"; then
  echo "FAIL: 정상 시험이 기대한 48회 검사를 완료하지 못함" >&2
  exit 1
fi

# ② 부정 시험: 관찰 경로의 PWM 값만 반전한다.
# 반드시 비정상 종료 + 전용 진단 문자열을 동시에 확인해야 통과.
if (cd "$OUT" && vvp ./sim.vvp +INJECT_FAULT >fault_injection.log 2>&1); then
  echo "FAIL: 주입한 PWM 관찰 오류를 검출하지 못함" >&2
  exit 1
fi

  mv "$OUT/ch10_pwm_corner_reset_timeout.vcd" "$OUT/fault_injection.vcd"
fi
grep -q 'DETECTED_INJECTED_FAULT' "$OUT/fault_injection.log" || {
  echo "FAIL: PWM 관찰 오류 대신 다른 이유로 실패함" >&2
  exit 1
}
echo "PASS HARNESS: 의도한 PWM 관찰 오류 검출"

# ③ 부정 시험: 듀티 8의 cfg_apply를 누락하여 적용 타임아웃을 검사한다.
if (cd "$OUT" && vvp ./sim.vvp +INJECT_TIMEOUT >apply_timeout.log 2>&1); then
  echo "FAIL: 누락한 cfg_apply를 타임아웃으로 검출하지 못함" >&2
  exit 1
fi
if [[ -f "$OUT/ch10_pwm_corner_reset_timeout.vcd" ]]; then
  mv "$OUT/ch10_pwm_corner_reset_timeout.vcd" "$OUT/apply_timeout.vcd"
fi

  exit 1
}

echo "PASS CH10 SUITE: 정상 1회 + 의도된 오류 검출 2회"
echo "로그: $OUT/{normal,fault_injection,apply_timeout}.log"

실습 설명 · 부정 실행의 실패를 harness가 판정한다

Harness(하니스, 여러 실행을 관리하는 검사 스크립트)는 정상 모드의 종료 성공과 정확한 PASS 행을 확인합니다. 두 부정 모드는 비정상 종료를 요구하고 전용 진단을 추가 확인합니다. 예를 들어 문법 오류로 실행이 끝난 것은 INJECT_FAULT 검출 성공이 아닙니다.

원본 XSIM 명령은 설치 버전의 Fatal 종료 코드 처리를 확인하는 수동 검토 경로입니다. Icarus 스크립트는 실패를 조건문 안에서 처리해, 예상한 비정상 종료 때문에 전체 셸이 즉시 끊기지 않도록 합니다. 마지막 PASS SUITE는 세 실행 결과를 묶은 판정이고 부정 TB 자체가 정상 종료했다는 뜻은 아닙니다. 기존 실측 로그를 보존하며 새로운 RTL_SIM은 NOT_RUN입니다.

07예상 결과와 오류 분석

다음은 시간 계약 및 코드 경로로 계산한 예상 출력입니다. 실제 시뮬레이터의 실행 로그가 아닙니다.

정상 실행의 기대 완료 문자열

부정 실행의 기대 진단

DETECTED_APPLY_TIMEOUT duty=8 deadline=10clks
자동 시험의 기대 완료 문자열

부정 로그에 FATAL이 있으면 DUT가 고장인가요? 의도된 외부 관찰 반전 또는 요청 누락을 검출한 결과입니다. 전용 메시지와 모드를 확인해야 하며 정상 DUT 결함으로 단정하지 않습니다.

왜 첫 0%도 설정을 요청하나요? 리셋값은 duty0이지만 enable0입니다. 정상 0% 상태 enable1을 적용해 두어야 뒤 요청 누락에서 기존 상태 보존을 확인할 수 있습니다.

두 오류를 찾았으면 모든 결함을 찾나요? 검사한 주입 위치와 시나리오의 검출 증거입니다. 모든 RTL 변이, 입력 공간, 샘플 사이 글리치의 검출률을 증명하지 않습니다. 다음 SVA는 정해진 시간 관계를 속성으로 명시합니다.
