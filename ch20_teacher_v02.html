01원본 PWM RTL 전체

클록은 10ns, RESET_PERIOD=8입니다. cfg_apply에서 저장한 설정은 주기 경계에 반영됩니다. 내부 상태는 동기 리셋, pwm_out은 resetn으로 조합 차단합니다.

reference_rtl/pwm_core.v · Verilog
`timescale 1ns/1ps
// P2-04: 보드와 무관한 단일 채널 범용 PWM 코어.
// (추가) period와 duty는 클록 횟수 단위. 0%/100%는 지속 LOW/HIGH.
// (추가) 설정은 주기 마지막 경계에서만 활성값으로 반영.
module pwm_core #(
    parameter [31:0] RESET_PERIOD = 32'd100000
)(
    input  wire        clk,
    input  wire        resetn,
    input  wire        cfg_apply,
    input  wire [31:0] cfg_period,
    input  wire [31:0] cfg_duty,
    input  wire        cfg_enable,
    input  wire        cfg_polarity,
    output wire        pwm_out,
    output reg         pending,
    output reg [31:0] active_period,
    output reg [31:0] active_duty,
    output reg         active_enable,
    output reg         active_polarity
);
    reg [31:0] counter;
    reg [31:0] shadow_period;
    reg [31:0] shadow_duty;
    reg        shadow_enable;
    reg        shadow_polarity;

    wire boundary = (counter >= active_period - 32'd1);
    wire duty_high = (counter < active_duty);

    // (주의) enable=0이면 polarity와 관계없이 LOW로 차단.
    // (설명) 기본 polarity에서 active_duty=0이면 항상 LOW,
    //         active_duty=active_period이면 항상 HIGH.
    assign pwm_out = resetn && active_enable &&
                     (active_polarity ? !duty_high : duty_high);

    always @(posedge clk) begin
        if (!resetn) begin
            counter         <= 32'd0;
            active_period   <= RESET_PERIOD;
            active_duty     <= 32'd0;
            active_enable   <= 1'b0;
            active_polarity <= 1'b0;
            shadow_period   <= RESET_PERIOD;
            shadow_duty     <= 32'd0;
            shadow_enable   <= 1'b0;
            shadow_polarity <= 1'b0;
            pending         <= 1'b0;
        end else begin
            if (boundary) begin
                counter <= 32'd0;
                if (pending) begin
                    active_period   <= shadow_period;
                    active_duty     <= shadow_duty;
                    active_enable   <= shadow_enable;
                    active_polarity <= shadow_polarity;
                    pending         <= 1'b0;
                end
            end else begin
                counter <= counter + 32'd1;
            end
            // (추가) 경계와 APPLY가 겹치면 새 값은 다음 경계에 적용.
            // 여러 APPLY가 겹치면 최종 요청값을 우선하는 단일 Shadow 구조.
            if (cfg_apply) begin
                shadow_period   <= cfg_period;
                shadow_duty     <= cfg_duty;
                shadow_enable   <= cfg_enable;
                shadow_polarity <= cfg_polarity;
                pending         <= 1'b1;
            end
        end
    end
endmodule

정상 출력은 활성화 상태에서 위상 0부터 duty 미만까지 HIGH입니다. 이번 장은 기본 극성과 고정 주기 8의 순차 요청만 다루며 내부 counter를 직접 관찰하지 않습니다.

02Factory · 생성 타입 교체

Factory 등록 및 생성 · 실제 핵심 구문

기반 클래스의 create 호출은 유지하지만 실제 객체는 파생 클래스 pwm20_traced_driver가 됩니다. 교체 등록은 하위 Agent가 Driver를 생성하기 전에 이루어져야 합니다. virtual drive_one은 실제 객체의 구현을 호출합니다. 파생 클래스는 로그를 남기고 super.drive_one(req)로 기존 구동을 수행한 뒤 trace_count를 증가시킵니다. $cast와 3개 완료 수로 교체 타입과 실행을 모두 확인합니다.

Factory 판서 · 변수 타입과 실제 객체 타입은 다를 수 있다

Agent의 drv 선언과 create 요청 타입은 pwm20_driver입니다. Test가 하위 생성 전에 type override를 등록하면 실제 객체는 pwm20_traced_driver입니다. 기반 타입 핸들에 파생 객체를 담을 수 있고 virtual drive_one 호출은 파생 구현으로 갑니다. 파생 구현은 기록→super 구동→trace_count 증가 순서입니다.

$cast(traced,env.ag.drv)는 현재 객체가 파생 타입인지 확인하며 새 객체를 만들거나 변환 복사하지 않습니다. trace_count3은 그 파생 동작이 세 거래에서 실제 끝났음을 확인합니다. new로 직접 생성한 객체에 Factory override가 자동 적용된다고 설명하면 안 됩니다.

settings는 Test가 생성하는 pwm20_cfg 객체입니다. Config DB는 env.ag.drv와 env.sb의 정확한 경로에 이 객체의 참조를 전달합니다. Sequence는 seq.cfg = settings로 직접 받습니다. build_phase 이후 같은 객체인지 확인합니다. 공유 객체는 자동 복제되지 않으므로 실행 중 임의 변경하지 않습니다. 설정값 자체의 독립성은 외부 시나리오 계약과 실행 스크립트의 계획별 결과 비교에서 확보하며, Driver와 Scoreboard가 설정 객체를 공유한다는 사실을 숨기지 않습니다.

배열 길이와 거래 수는 3으로 고정하고 듀티 0~8만 허용합니다. max_wait_cycles와 max_apply_ns는 이 실습의 제한이며 별도 변화 시험은 아닙니다. 제19장의 독립 위상 계산은 그대로 유지합니다. Monitor는 매 상승 에지 +1ns에 새 객체를 보내고 Scoreboard는 cycles % 8로 기대 위상을 계산하여 모든 공개 출력을 비교합니다.

Config DB 판서 · 같은 핸들은 같은 설정을 가리킨다

settings 하나를 Driver와 Scoreboard의 정확한 경로에 set하고 Sequence에는 seq.cfg=settings로 직접 전달합니다. 자동 복제가 아니므로 세 핸들은 같은 객체를 봅니다. CFG_IDENTITY는 값만 같은 다른 객체도 구분합니다. 실행 중 한쪽에서 duty_plan을 바꾸면 다른 쪽 기대값도 바뀔 수 있어 구성 후 고정해서 사용합니다.

기본2·6·0과 대안1·8·3은 시나리오 계약입니다. 구동·판정이 설정을 공유하므로 설정 자체 오류까지 완전히 독립적으로 검출한다고 주장할 수 없습니다. 실행기가 계획별 RESULT와 trace duty3개를 별도로 요구하여 의도한 두 계획이 실행되었는지 대조합니다. 배열3개·거래3개와 duty0~8은 build에서 확인합니다.

        function void write(pwm20_sample sample);
            if (sample.resetn === 1'b0) begin
                if (cycles != 0)
                    `uvm_fatal("SB_RESET", "Unexpected reset during transactions")
                reset_samples++;
                if (sample.period !== 32'd8 || sample.duty !== 32'd0 ||
                    sample.enable !== 1'b0 || sample.polarity !== 1'b0 ||
                    sample.pending !== 1'b0 || sample.pwm !== 1'b0)
                    `uvm_fatal("SB_RESET", "Reset output mismatch")
                return;
            end
            if (sample.resetn !== 1'b1 || reset_samples != 3)
                `uvm_fatal("SB_RESET", "Reset sequence mismatch")
            cycles++;
            phase_idx = cycles % 8;

            // 주기 경계에서는 이전 요청만 적용된다.
            if (phase_idx == 0 && expected_pending) begin
                if (applied >= requests || applied >= cfg.expected_transactions)
                    `uvm_fatal("SB_ORDER", "Apply without request")
                expected_duty = cfg.duty_plan[applied];
                expected_enable = 1;
                expected_pending = 0;
                if (sample.sampled_at - request_time[applied] > cfg.max_apply_ns)
                    `uvm_fatal("SB_LATENCY", "Apply exceeded one period")
                applied++;
                `uvm_info("SB", $sformatf("APPLIED %0d duty=%0d",
                    applied, expected_duty), UVM_LOW)
            end
            // 요청의 예상 순서는 Driver의 거래 객체에 의존하지 않는다.
            if (sample.cfg_apply === 1'b1) begin
                if (requests >= cfg.expected_transactions || expected_pending)
                    `uvm_fatal("SB_EXTRA", "Unexpected or overlapping request")
                if (sample.cfg_period !== 32'd8 ||
                    sample.cfg_duty !== cfg.duty_plan[requests] ||
                    sample.cfg_enable !== 1'b1 || sample.cfg_polarity !== 1'b0)
                    `uvm_fatal("SB_REQUEST", "Unexpected PWM request content")
                request_time[requests] = sample.sampled_at;
                requests++;
                expected_pending = 1;
                `uvm_info("SB", $sformatf("REQUEST %0d duty=%0d",
                    requests, sample.cfg_duty), UVM_LOW)
            end else if (sample.cfg_apply !== 1'b0)
                `uvm_fatal("SB_REQUEST", "Unknown cfg_apply")

            // 실제 공개 출력과 독립 기대값을 매 에지에서 대조한다.
            if (sample.period !== 32'd8 || sample.duty !== expected_duty ||
                sample.enable !== expected_enable || sample.polarity !== 1'b0 ||
                sample.pending !== expected_pending)
                `uvm_fatal("SB_STATE", $sformatf("t=%0d phase=%0d",
                    sample.sampled_at, phase_idx))

            if (sample.pwm !== expected_pwm)
                `uvm_fatal("SB_PWM", $sformatf("t=%0d phase=%0d expected=%0b got=%0b",
                    sample.sampled_at, phase_idx, expected_pwm, sample.pwm))
            if (expected_enable) samples++;
        endfunction

check_normal() {
  local log="$1" plan="$2" a="$3" b="$4" c="$5"
  grep -Eq "\[RESULT\][[:space:]]+PASS CH20 factory=traced plan=$plan applied=3 samples=24[[:space:]]*$" "$log"

  grep -Eq 'UVM_FATAL[[:space:]]*:[[:space:]]*0[[:space:]]*$' "$log"

예상 문답 · 세 도구의 책임

Config DB로 Driver 타입도 바꾸나요? 이 코드의 타입 선택은 Factory override이고 Config DB는 cfg·vif 참조 전달입니다. 각각 실제 호출 위치를 구별합니다.

trace_count가3이면 검증 완료인가요? Driver의 세 구동이 끝난 증거입니다. 마지막 출력7표본이 남을 수 있어 Scoreboard24표본과 phase 최종 검사를 함께 확인해야 합니다.

timeout 설정도 다양하게 검증했나요? max_wait_cycles12·max_apply_ns80은 현재 두 계획에서 고정입니다. 설정 필드가 있다는 사실과 경계값 변화 시험을 실제 수행했다는 사실은 다릅니다.

추가 교수용 문답

Factory와 상속은 같은 기능인가요? 상속은 타입 관계를 정의하고 Factory는 생성 요청의 실제 타입을 선택합니다. virtual 호출은 생성 이후 실제 타입의 구현을 선택합니다.

trace_count=3이면 로그도 반드시 세 줄인가요? trace_count는 기반 구동 반환 후 증가하고 메시지는 enable_trace와 verbosity에 의존합니다. 현재 실행기는 두 계획의 로그도 별도로 검사합니다.

Config DB가 설정 객체를 복제하나요? 여기서는 핸들 전달입니다. 객체 동일성을 검사하고, Sequence의 직접 대입도 같은 객체를 가리킵니다.

Objection을 계속 올리면 성공인가요? 종료를 보류할 뿐입니다. 실제 검사와 완료 조건, 별도 watchdog가 필요합니다.
