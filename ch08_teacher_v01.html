교수용 이론 · 시험 요청을 하나의 객체로

제05장의 구조체는 관련 값을 묶고, 클래스는 그 값과 생성 규칙·설명 동작을 함께 묶습니다. ‘출력 가능한 문자를, valid=1·ready=0인 상태로 시험하라’는 요청을 객체에 담으면 입력 선택과 실제 신호 대입을 분리할 수 있습니다. 이 장은 원리를 보기 위해 평면 포트로 돌아오며 제07장 interface 코드를 구현한 것처럼 설명하지 않습니다.

01원본 RTL과 검증 구조

DUT(디유티, 검증 대상 회로)는 데이터와 유효 신호를 전달하고 준비 신호를 역방향으로 전달하는 조합 회로입니다. UART 직렬 송수신기 전체가 아니며 클록과 리셋, 저장소가 없습니다.

그림 읽기 · 상속 화살표와 신호선을 구별하기

uart_stall_txn과 uart_txn 사이의 extends는 언어의 타입 관계입니다. FPGA 배선이나 회로 하위 인스턴스가 아닙니다. apply_and_check가 객체의 data·valid·ready를 읽어 세 실제 DUT 입력에 쓰는 지점에서 추상 요청이 신호가 됩니다. 오른쪽 DUT는 여전히 같은 세 assign입니다.

그림의 클래스 이름은 설계 형식이고 normal·stalled는 객체를 가리키는 핸들 이름입니다. 이들을 실제 module 인스턴스 dut와 같은 계층으로 세지 않습니다. 이러한 구분은 뒤의 UVM에서 거래 객체와 component 계층을 구별하는 기반이 됩니다.

02Class와 new · 핸들과 객체

Class(클래스, 객체의 자료와 동작을 정의하는 형식)는 한 입력 사례를 data·valid·ready로 묶습니다. uart_txn normal;은 객체를 참조할 핸들 선언이고 normal = new();를 실행하면 생성자가 초기값을 설정합니다. 선언만으로 DUT 입력을 구동하지 않습니다.

SystemVerilog · 실제 클래스 선언의 일부
class uart_txn;
    rand bit [7:0] data;
    rand bit       valid;
    rand bit       ready;
    // 제약 및 describe()는 전체 코드 참조
    function new();
        data = 8'h41;
        valid = 1'b1;
        ready = 1'b1;
    endfunction
endclass

객체 핸들을 다른 변수에 대입하거나 태스크 인자로 전달해도 객체의 내용이 자동 복제되는 것은 아닙니다. 이번 검사는 객체를 읽기만 하며 실행 중 별도의 동시 변경이 없습니다. 2상태 bit는 정상 0/1 입력을 생성하는 데 쓰고, DUT 입력 관찰용 logic과 출력 wire는 4상태를 유지합니다.

핸들·객체·필드의 세 단계

uart_txn normal;은 참조를 담을 핸들만 선언합니다. new 전에는 null이므로 필드에 접근할 객체가 없습니다. normal=new();에서 객체를 만들고 생성자가 data=41, valid=1, ready=1을 정합니다. 이후 normal.data가 객체의 필드를 가리킵니다.

구조체 대입과 달리 핸들 대입은 기본적으로 같은 객체를 가리키게 합니다. task의 input uart_txn tr에도 객체를 통째로 복제하는 것이 아니라 핸들이 전달됩니다. 현재 task는 읽기만 하고 다른 절차가 같은 객체를 동시에 바꾸지 않습니다. 나중에 비동기 처리나 큐에 객체를 보관할 때는 같은 객체를 재사용하며 덮어쓰지 않는지 확인해야 합니다.

new와 randomize는 다릅니다. 자식 객체도 생성 직후에는 부모 생성자의 초기값을 받으며, c_stall이 그 순간 ready를 자동으로 0으로 바꾸지는 않습니다. 제약은 randomize 호출 때 적용됩니다. 임의 필드 대입도 제약을 자동으로 확인하지 않습니다.

03Rand·constraint · 허용 입력 공간

rand(랜드, 무작위 생성 대상 속성)는 randomize() 호출에서 변경할 수 있는 필드를 나타냅니다. constraint(컨스트레인트, 허용 조건)는 생성값의 범위를 제한합니다.

SystemVerilog · 실제 제약
constraint c_printable { data inside {[8'h20:8'h7e]}; }
// 호출 시점의 추가 제약
if ((normal.randomize() with { valid == 0; ready == 1; }) == 0)
    $fatal(1, "RANDOMIZE_FAIL IDLE");

0x20~0x7E는 출력 가능한 ASCII(아스키, 문자 코드) 95개입니다. 부모 클래스에서는 valid와 ready가 각각 0 또는 1이므로 전체 허용 조합은 95 × 2 × 2 → 380개입니다. IDLE 호출은 valid=0, ready=1을 추가하여 95개 조합으로 제한합니다. 이는 가능한 입력 공간의 크기이지 실제로 95개 또는 380개를 시험했다는 뜻은 아닙니다.

randomize()가 0을 반환하면 실패입니다. 생성 성공 이후에도 실제 값이 제약을 만족하는지 검사합니다. 예를 들어 printable 제약과 data=0을 동시에 강제하면 허용 조합이 없습니다. 일반 필드 직접 대입은 제약을 자동으로 검사하지 않습니다.

판서 · 허용 공간과 실제 시험 수

0x20=32, 0x7E=126이므로 양끝을 포함한 문자 수는 126-32+1=95입니다. 부모의 조합 공간은 95×2×2=380입니다. IDLE 인라인 제약 valid=0·ready=1을 추가하면 95개, 자식 STALL 제약 valid=1·ready=0도 95개입니다. 이것은 가능한 값의 수이며 실행된 난수 사례 수가 아닙니다.

제약은 명령 실행 순서가 아니라 동시에 만족해야 하는 조건입니다. 출력 가능한 범위와 data=0을 함께 요구하면 교집합이 비어 생성에 실패합니다. randomize 성공 여부를 확인한 다음 실제 필드도 다시 검사하는 이유는 입력 생성 도구의 성공과 시험 계약을 구분하기 위해서입니다. 무작위라는 말로 모든 값의 균등 출현이나 전수 검사를 보장하지 않습니다.

04Extends · 상속과 부모 타입 재사용

extends(익스텐즈, 상속)는 부모의 필드·메서드·제약을 자식에서 재사용합니다. 아래 자식 클래스는 출력 가능한 문자 범위를 물려받고 c_stall로 정지 사례를 제한합니다.

SystemVerilog · 실제 자식 클래스
class uart_stall_txn extends uart_txn;
    constraint c_stall { valid == 1'b1; ready == 1'b0; }
endclass

apply_and_check(input uart_txn tr, ...)는 부모 클래스 핸들 인자를 사용하므로 자식 객체도 전달할 수 있습니다(업캐스팅). 실제 객체의 필드를 읽어 공통 검사를 재사용합니다. 이 예제는 virtual 메서드의 재정의나 동적 디스패치를 구현하지 않습니다. 마지막 사례의 기존 로그 이름은 유지하되, 새로운 난수 생성이나 별도 가상 메서드 시험으로 계산하지 않습니다.

상속을 실제로 사용한 부분

자식은 data·valid·ready, c_printable, new와 describe의 기본 동작을 재사용하고 c_stall을 더합니다. 부모 타입을 받는 apply_and_check에 자식 핸들을 전달하면 부모가 가진 필드를 같은 방식으로 읽을 수 있습니다. 이를 업캐스팅이라고 합니다.

현재 describe는 virtual로 선언되지 않았고 자식의 재정의도 없습니다. 따라서 POLYMORPHIC_STALL이라는 기존 로그 이름을 가상 메서드 동적 선택을 검증한 증거로 해석하지 않습니다. 마지막 호출은 직전 stalled 객체를 그대로 다시 검사하므로 데이터가 같아야 합니다. 새로운 네 번째 난수 생성도 아닙니다.

05테스트벤치 전체 코드

부모 객체의 직접 입력 → IDLE 제약 생성 → 자식의 STALL 제약 생성 → 자식 객체 재사용 순서로 네 번 검사합니다. 모든 검사에서 원본 RTL의 세 조합 연결을 확인합니다.

tb/ch08/tb_uart_objects.sv · SystemVerilog
`timescale 1ns/1ps
// 제08장: 원본 UART Echo의 6개 포트를 변경하지 않고 객체 기반 입력을 검증한다.
// class, new, extends, rand, constraint, randomize()를 직접 실습한다.

class uart_txn;
    rand bit [7:0] data;
    rand bit       valid;
    rand bit       ready;

    // (추가) 출력 가능한 ASCII(아스키) 문자 범위로 데이터를 제한한다.
    constraint c_printable { data inside {[8'h20:8'h7e]}; }

    function new();
        data = 8'h41;
        valid = 1'b1;
        ready = 1'b1;
    endfunction

    function string describe();
        return $sformatf("data=%02h valid=%0b ready=%0b",
                         data, valid, ready);
    endfunction
endclass

// (추가) 부모의 데이터 범위 제약을 물려받고 정지 조건을 추가한다.
class uart_stall_txn extends uart_txn;
    constraint c_stall { valid == 1'b1; ready == 1'b0; }
endclass

module tb_uart_objects;
    logic [7:0] rx_data_i;
    logic       rx_valid_i;
    wire        rx_ready_o;
    wire [7:0]  tx_data_o;
    wire        tx_valid_o;
    logic       tx_ready_i;

    integer checked = 0;
    uart_txn normal;
    uart_stall_txn stalled;

    // 원본 DUT: 데이터/유효/준비를 그대로 전달하는 조합회로이다.
    uart_echo_controller dut (
        .rx_data_i(rx_data_i),
        .rx_valid_i(rx_valid_i),
        .rx_ready_o(rx_ready_o),
        .tx_data_o(tx_data_o),
        .tx_valid_o(tx_valid_o),
        .tx_ready_i(tx_ready_i)
    );

    // (추가) 객체의 속성을 DUT 포트에 적용하고 4상태 비교로 확인한다.
    task automatic apply_and_check(input uart_txn tr, input string label_name);
        begin
            rx_data_i  = tr.data;
            rx_valid_i = tr.valid;
            tx_ready_i = tr.ready;
            #1; // 조합 출력이 안정되도록 TB에서만 기다린다. DUT 지연이 아니다.
            if ((tx_data_o !== tr.data) ||
                (tx_valid_o !== tr.valid) ||
                (rx_ready_o !== tr.ready))
                $fatal(1, "FAIL %s expected %s got %02h/%b/%b",
                       label_name, tr.describe(), tx_data_o,
                       tx_valid_o, rx_ready_o);
            checked++;
            $display("PASS %s %s", label_name, tr.describe());
        end
    endtask

    initial begin
        $display("=== CH08 OBJECT / CONSTRAINT START ===");
        normal = new();
        stalled = new();

        // (추가) 부모 객체에 특정 값을 넣어 기준 동작부터 확인한다.
        normal.data = 8'h41;
        normal.valid = 1'b1;
        normal.ready = 1'b1;
        apply_and_check(normal, "DIRECT_A");

        // (추가) 인라인 제약으로 유효한 IDLE 사례를 생성한다.
        if ((normal.randomize() with { valid == 0; ready == 1; }) == 0)
            $fatal(1, "RANDOMIZE_FAIL IDLE");
        // (추가) 생성 성공뿐 아니라 실제 IDLE 제약 만족 여부도 검사한다.
        if (!(normal.data >= 8'h20 && normal.data <= 8'h7e &&
              normal.valid == 1'b0 && normal.ready == 1'b1))
            $fatal(1, "CONSTRAINT_FAIL IDLE");
        apply_and_check(normal, "RANDOM_IDLE");

        // (추가) 상속된 제약은 데이터 범위를 유지하고 정지를 강제한다.
        if (stalled.randomize() == 0) $fatal(1, "RANDOMIZE_FAIL STALL");
        if (!(stalled.data >= 8'h20 && stalled.data <= 8'h7e &&
              stalled.valid == 1'b1 && stalled.ready == 1'b0))
            $fatal(1, "CONSTRAINT_FAIL STALL");
        apply_and_check(stalled, "RANDOM_STALL");

        // (추가) 부모 타입 인자로 자식 객체를 전달해 공통 검사 태스크를 재사용한다.
        apply_and_check(stalled, "POLYMORPHIC_STALL");
        if (checked != 4) $fatal(1, "COUNT_FAIL %0d", checked);
        $display("CH08 PASS: %0d cases checked", checked);
        $finish;
    end

    initial begin
        #100;
        $fatal(1, "CH08 TIMEOUT");
    end
endmodule

제약은 입력 생성 정책이고 apply_and_check()는 DUT 정답 비교입니다. 제약이 정상이라는 사실만으로 출력도 정상이라고 판단하지 않습니다.

전체 코드의 인과관계 · 생성→조건 확인→구동→비교

두 객체를 만든 뒤 직접 A를 한 번 검사하고, 부모 IDLE 무작위화 한 번, 자식 STALL 무작위화 한 번, 같은 자식 재사용 한 번을 수행합니다. 객체 생성과 randomize는 시뮬레이션 시간 지연을 지정하지 않습니다. 실제 시간은 각 task의 #1에서 진행하므로 네 비교는 1·2·3·4ns입니다. 해결기가 쓰는 실제 CPU 실행 시간과 시뮬레이션 ns는 다릅니다.

apply_and_check는 객체에서 값을 포트에 복사하고, 안정화 대기 뒤 같은 객체를 기대값으로 사용해 출력 세 개를 비교합니다. 제약 만족은 입력이 허용된다는 뜻이고, 이 비교의 성공은 DUT가 그 입력을 올바르게 연결했다는 뜻입니다. 두 검사는 서로 대체하지 않습니다.

예상 문답 · 객체가 해결하지 않는 것

rand라고 선언하면 값이 계속 바뀌나요? randomize를 호출할 때 생성합니다. 선언이나 new만으로 계속 난수가 생기지 않습니다.

객체를 DUT에 주면 알아서 신호가 되나요? 아닙니다. apply_and_check 안의 세 대입이 필요합니다. UVM에서는 이후 Driver가 이런 변환에 시간·프로토콜을 더합니다. 현재 코드에는 UVM Sequence·Driver·Factory가 없습니다.

네 번 PASS면 380조합을 검증했나요? 직접 입력 1회, 생성 2회, 재사용 1회뿐입니다. 큰 공간을 탐색하려면 반복·시드·커버리지·오류 시나리오를 설계해야 합니다. 다음 장은 입력 표현보다 기대 동작의 독립성과 매 클록 비교를 확장합니다.
